REVISED SYSTEM ANALYSIS
========================

Basis: COMSC 6 Laboratory Activity — Revising a Shabby Student Attendance System

1. ACCEPTABILITY
-----------------
Problems addressed:
- Unclear/flat navigation -> reusable header/navigation.
- Blank forms accepted -> server-side validation and required-field indicators.
- No useful success/failure feedback -> success and error messages.
- Accidental deletion -> confirmation before deletion.
- Poor mobile usability -> responsive CSS.
- Difficult student lookup -> search and pagination.
- Weak table presentation -> responsive table container and clearer columns.
- No edit feature in the shabby starter -> dedicated edit page.

2. DEPENDABILITY & SECURITY
---------------------------
Problems addressed:
- Plaintext password -> password_hash/password_verify.
- SQL injection in login -> prepared statement.
- Unsafe student ID -> integer validation plus prepared DELETE.
- Raw SQL errors exposed -> technical errors logged; users receive safe messages.
- Missing authentication centralization -> includes/auth.php.
- Duplicate attendance -> UNIQUE(student_id, attendance_date).
- Invalid attendance status -> ENUM plus server-side allow-list validation.
- Unsafe session handling -> session regeneration after login and safe logout.

3. EFFICIENCY
-------------
Problems addressed:
- Implicit old-style report join -> explicit INNER JOIN.
- No useful indexes -> indexes for student number, attendance date, attendance student ID, and student name.
- All student records loaded at once -> pagination.
- No filtering -> student search and report filtering.
- Unnecessary columns -> SELECT only fields used by each page.
- Repeated attendance inserts -> one prepared statement reused in a transaction.

4. MAINTAINABILITY
------------------
Problems addressed:
- Database connection mixed with page logic -> config/database.php.
- Repeated authentication code -> includes/auth.php.
- Repeated page layout -> includes/header.php and includes/footer.php.
- Flat project structure -> config/includes/students/attendance/reports/css folders.
- Repeated validation/processing patterns -> organized processing pages.
- Unclear responsibilities -> separate CRUD, attendance, report, configuration, and presentation files.

5. DATABASE REVISION
--------------------
The revised database includes:
- UNIQUE username.
- UNIQUE student number.
- UNIQUE student/date attendance combination.
- Foreign key from attendance.student_id to students.id.
- Cascading delete for attendance when a student is deleted.
- ENUM attendance status.
- Required indexes.

6. VALIDATION
-------------
The revised system rejects:
- Empty student number.
- Student number over 30 characters.
- Empty/overlong first name.
- Empty/overlong last name.
- Empty/overlong course.
- Invalid attendance date.
- Missing attendance submissions.
- Invalid student IDs.
- Invalid attendance statuses.

7. IMPORTANT DIFFERENCE
-----------------------
The shabby version demonstrates what can happen when a system is made only to "work."
The revised version applies the four required quality characteristics:
Acceptability, Dependability & Security, Efficiency, and Maintainability.

The laboratory still requires before/after evidence and problem analysis for submission. This ZIP is provided so the revised implementation can be compared directly with the shabby version.
