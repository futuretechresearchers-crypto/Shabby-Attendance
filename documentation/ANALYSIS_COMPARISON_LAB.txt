COMSC 6 SOFTWARE ENGINEERING LABORATORY
Revising a Shabby Student Attendance System — From “It Works” to “It’s Good Software”

I. INTRODUCTION
The laboratory compares a minimally functional attendance program with a revised program that improves acceptability, dependability/security, efficiency, and maintainability. A page that accepts data is not necessarily safe, understandable, reliable, or practical as records grow.

II. PROJECT OVERVIEW
The local original-style demo provides administrator login, dashboard navigation, student listing/add/delete, attendance entry, report, and logout. It uses prefixed `unrevised_*` tables and a separate PHP session. The existing revised project is maintained at the repository root and includes a richer dashboard, student create/edit/search/pagination, attendance recording, filtered report, reusable layout, and responsive CSS.

IV. ACCEPTABILITY ANALYSIS
The demo retains simple blue headings, buttons, tables, and navigation. Revised pages share a sidebar/header, labeled forms, required markers, clear feedback, responsive styling, improved tables, student search, date formatting, and confirmation before student deletion. The revised login displays a version label and a working switch link.

V. DEPENDABILITY AND SECURITY
Revised authentication uses a prepared username lookup and password_verify, then regenerates the session ID. Protected pages call requireLogin. Revised writes use prepared statements; attendance validates dates/status/positive IDs and runs in a transaction. Revised deletion is POST-only and checks a session CSRF token. Outputs are escaped. Database connection failure is logged and shown as a generic message. Referential integrity depends on the live attendance foreign key; it could not be inspected in this session.

VI. EFFICIENCY
The revised student list uses selected columns, server-side search, and pagination. The attendance report filters and paginates 25 records and uses explicit INNER JOIN. The existing schema script described indexes for student number/name and attendance date/student/student-date, but exact live indexes and query plans were not available. No benchmark or EXPLAIN result is claimed.

VII. MAINTAINABILITY
The revised project separates configuration, authentication/layout includes, students, attendance, reports, and CSS. CSRF helpers are centralized with authentication. Routes use named files and prepared writes. The existing dashboard and student editing functionality were preserved. The demo remains separate for teaching comparison, with a separate session namespace and table prefix.

IX. DATABASE IMPROVEMENTS
The demo gets separate `unrevised_users`, `unrevised_students`, and `unrevised_attendance` tables, seeded idempotently with the sample people. Its schema intentionally models weak original behavior. The revised migration checks duplicates and adds missing safe keys/column constraints idempotently. The live schema has a unique username key, unique student number/date keys, and ENUM attendance status. There is no FK: two orphan records were found and preserved. The old root database.sql contained DROP TABLE commands and was replaced by a non-destructive notice.

X. FEATURE COMPARISON
Original requirements retained in the demo: admin login/logout, dashboard links, student list/add/delete, attendance entry/save, and attendance report. Revised existing features preserved: dashboard trends/summary/recent activity, student edit/search/pagination, attendance filters, and responsive layout. Added for this comparison: version routes, separate sessions and database namespaces, demo-only warning, CSRF deletion/attendance writes, and report pagination.

XI. REFLECTION QUESTIONS
Is the interface understandable? The simple demo's labels and navigation are visible, but feedback and validation are sparse. Revised navigation is shared and consistent.
Are labels and navigation consistent? Revised pages reuse the same shell; the demo uses a small static navigation row.
Does the application prevent accidental deletion? Demo does not. Revised deletion asks for confirmation and uses a POST form.
Does it give meaningful feedback? Revised create, attendance, and delete flows use messages; database failures are generalized. Runtime observation is pending.
Why is plaintext password storage unsafe? A table disclosure immediately reveals usable credentials, including reused passwords. Hashing with password_hash/password_verify reduces that exposure.
Why are prepared statements necessary? They keep user-supplied values separate from SQL syntax and prevent input from changing query structure.
Why does duplicated authentication code reduce maintainability? Each copy can drift, leaving a route unprotected or behaving differently when policy changes.
How do indexing and pagination help growth? Indexes can reduce lookup work for matching access patterns; pagination caps rows rendered and transferred at a time. Actual benefit depends on schema, data, and query plan.
Why is “merely works” insufficient? Correctness of one happy-path action says little about security, data integrity, usability, performance at scale, or the ability to change the system safely.

XII. CONCLUSION
Source changes improve the revised version's interface consistency, feedback, access control, request validation, CSRF protection, and report scalability. Database guarantees must still be checked against the actual local database before claiming complete integrity.
